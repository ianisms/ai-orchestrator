# Threat model: agent delegation path (prototypes A and C)

Path: user consents at the STS > gateway exchanges for a tool token or a handoff >
sub-agent exchanges the handoff > tool server verifies the token > PEP asks the PDP > tool runs > output returns to the model.

Scope: the prototypes in delegation/ and policy/ (threats 1-15), and the voice gate in the live orchestrator (threats 16-22). The live assistant does not use the delegation and policy prototypes yet.

Assume breach: any agent can be steered by text it reads, and any token an agent holds can leak.
Goal: a steered or compromised agent can do no more than the user approved, for no longer than a few minutes, and every attempt leaves a record.

| # | Threat | Control | Tested | Residual risk |
|---|---|---|---|---|
| 1 | Replay of an expired or stolen tool token | Tool tokens live 120-300 s, no refresh; tool rejects expired tokens; token age checked again in policy. Sender constraint (RFC 9449 DPoP, `delegation/dpop.py`): every token is bound by `cnf.jkt` to the P-256 key of the client that presents it (actor and tool tokens to the requester, the user token to the consented agent, the handoff to the delegate), every `/token` call and every tool call carries a proof signed with that key naming the method, URI, time and a fresh `jti`, with `ath` over the token at the tool; the verifier checks the proof before the revocation state; `revoke_key(jkt)` kills every token bound to a key | Yes: expired replay refused at tool; stolen token with no proof, with a proof from another key, with its captured proof replayed, with a proof for another URI or older than 60 s all refused at tool; exchange without a proof, with an unbound token, or under another client's key refused at STS; header `jwk` with private material, wrong `typ` or `alg` refused; handoff usable by the delegate and not by the gateway; revoked key kills its tokens and its new proofs; `require_dpop=False` restores bearer behaviour | The key is software in the agent's process: this stops theft of the token, not compromise of the process (the hardware key and SVIDs are for that). mTLS-bound tokens (RFC 8705) wait for SVIDs. No server nonces; no key rotation. The handoff's binding is this STS's choice, not an RFC reading |
| 2 | Agent acts without the user's consent | Exchange requires `may_act` naming this actor, and `aud` naming it | Yes: no-consent exchange refused; another agent presenting the user's token refused | Consent screen is simulated in the Python STS; Keycloak hop 1 has the real one |
| 3 | Confused deputy: sub-agent gets more than its parent | Scope must be held by the subject and registered for the actor; audience must be registered; policy requires every actor in the chain to hold the tool | Yes: sub-agent asking for repo:write and for an unregistered tool refused at STS; merge refused by policy | Registration data is static; a wrong grant in config is a wrong grant everywhere |
| 4 | Scope or audience expansion through chained exchanges | Each hop intersects scope; handoff scope capped by the next actor's registration; depth capped at 2, counted at handoff | Yes: over-wide handoff and a third hop refused | Depth cap is a blunt limit; no per-chain policy beyond it |
| 5 | Act-chain stripping | Plain exchange of a token carrying `act` or `may_act` refused; tool rejects tokens without `act`; handoff tokens are addressed to an agent, never a tool | Yes: all three refused | None known in the prototype |
| 6 | Actor impersonation | Actor token must belong to the authenticated client; `may_act.sub` and `client_id` must match it; the DPoP proof at `client_credentials` must come from the client's registered key, so a leaked secret alone mints nothing | Yes: gateway using another agent's actor token refused; secret with an unregistered key refused | Client secrets plus a software key in process; workload identity (SPIFFE, prototype B) replaces both |
| 7 | Prompt injection drives a write | Write-class tools need the user's approval for that exact call, single use; sub-agents are not granted writes | Yes: injected merge refused via sub-agent and via gateway; approval bound to arguments and not replayable | Approval UX: a user who approves everything defeats it; channel simulated |
| 8 | Exfiltration through a read tool | Resource must be in the session's list | Partly: read of an out-of-session repo refused | Tool output is not inspected; data the user did allow can still flow back to the model |
| 9 | PDP outage or slow PDP | PEP fails closed on timeout, 5xx and malformed answers; 500 ms budget | Yes: OPA down and PDP timeout both denied and logged | Availability cost: outage stops all tool calls, by design |
| 10 | Forged tokens | RS256 signature checked against the STS key or JWKS; issuer and audience checked. DPoP proofs: ES256 only, signature checked against the header `jwk`, which must be public-only | Yes: token signed by another key refused; proof signed by a key other than its header `jwk`, HS256 proof, and `jwk` carrying `d` all refused | STS signing key and client DPoP keys held in memory in the prototype; no rotation |
| 11 | Revocation gap | Short lifetimes; lineage claims (`jti`, `parent_jti`, `grant_id`) on every token; RFC 7009 `/revoke` that also revokes a token's descendants and, for a user token, its grant; admin `revoke_grant` and `revoke_client`; STS refuses exchange of a revoked subject or lineage; tool verifier checks an in-memory denylist after local JWT verification, fail closed if the check errors; tool servers report the token they were presented with a reason and the STS escalates by its own policy (1 token, 2 the actor's delegation, 3 the grant, 10 minute window); admin routes behind an `sts:admin` actor token that no exchange can issue | Yes: user token revoked, live tool token refused at tool and re-exchange refused at STS; sibling handoff unaffected; unknown and expired tokens succeed silently; client outside the chain refused; denylist entry gone after exp; revoked client loses actor tokens and live tool tokens; revocation works with the PDP down; tool cannot revoke the handoff above it; two reports kill the sibling under the same handoff and not another actor's; third kills the grant; strikes outside the window do not add up; `sts:admin` refused on login and exchange; admin routes 401 for non-actor tokens and 403 for non-admin actors; admin revoke over HTTP kills live tool tokens | Denylist is in process: a tool that does not share it sees nothing (pushed deny list across PEPs not built); tokens are key-bound (#1) and `revoke_key` kills a key's tokens, but a verifier that does not share the denylist still sees nothing of it; a hostile or buggy tool server can take out an actor's delegation with two reports and a grant with three, by design, and nothing verifies the report was warranted; the ops-console is a client secret, not an SVID; Keycloak hop 1 does not participate (its `/revoke` knows only its own tokens; no introspection or admin-event feed on exchange) |
| 12 | Audit gaps | Every exchange and every tool decision logged with path, decision and reasons | Yes: counts checked in tests | Logs are in process; no tamper evidence or central sink |
| 13 | Stolen workload credential, Docker socket exposure | Not built (prototype B) | No | SPIRE's Docker attestor needs the Docker socket and pid: host, which is root-equivalent |
| 14 | Device posture spoofing; device-code phishing on headless agents | Posture as a policy input: not built (prototype D). Device identity for the speaker is built (`server/modules/orchestrator/core/device_identity.py`, `DEVICE_IDENTITY.md`): a non-extractable P-256 key in PIV slot 9a of a plugged-in YubiKey 5 answers a boot-time nonce challenge, and the orchestrator issues a 10 minute credential with the key thumbprint in `cnf`; enrollment is host-side and revocable | Yes: right key accepted; wrong key, expired nonce, replayed nonce, nonce for another device, unknown device, revoked device and missing key all denied and logged; credential carries `cnf` and expires | The key proves possession, not software state: no measured boot, no PCRs, so a reflashed CM5 with the YubiKey still attests. The credential is verified and logged at connect but not yet enforced or fed to the policy. Target is a secure element or SPI TPM on the next carrier-board revision |
| 15 | Voice spoofing: replayed recording, cloned voice, request from outside the home | Voice requests need a match of 0.98 or better, home-network origin and a passed liveness check; missing signals fail closed; writes confirm by default and high-risk tools always confirm | Yes: low match, failed liveness, off-network and missing signals all denied; high-risk merge denied with confirmations off | The policy trusts the front end's liveness result; a real-time voice clone that passes liveness still gets read access, so writes keep the confirmation. The orchestrator's voice gate (16-22) gathers these signals itself; liveness is not built yet |

## Voice gate in the live orchestrator (server/)

Path: speaker audio > orchestrator commits the turn > model requests a tool > gate decides > tool runs.

Mode: monitor. Every non-read decision is logged as `allow` or `would_deny`; nothing is blocked until the liveness check and the approval flows exist.

| # | Threat | Control | Tested | Residual risk |
|---|---|---|---|---|
| 16 | Model-driven identity: a steered model claims or picks who is speaking | The orchestrator identifies the speaker from the turn's own audio through `identify_speaker`, which is hidden from the model; the model supplies no input to the decision | Partly: decision logic unit tested; the hidden-tool wiring is reviewed, not tested | `get_person_id` still gives the model a session-scoped identity for per-person reads, and reads are not gated |
| 17 | Identity takeover by claiming a name ("I'm Alice") | A stated name records a pending enrollment only; it never joins a profile or sets the session identity; approval is out of band (`scripts/approve_enrollment.py`) | Partly: approval script tested; tool path reviewed | Approval is a host-side script until the phone flow exists |
| 18 | Spoofed origin through client-asserted headers, or a different host on a trusted address | Trusted speaker addresses are matched against the gRPC peer address; a request relayed through a proxy arrives from the proxy's address and is not trusted unless that address is configured. Device identity (#14, `DEVICE_IDENTITY.md`) adds a key the host cannot copy: the orchestrator verifies an `x-device-credential` from metadata at connect and logs the device id and key thumbprint | Yes: untrusted and malformed addresses fail; credential verify, tamper, forge, revoke and expiry tested | IPv4-mapped IPv6 peers need that form configured. The gate still decides on the address: the speaker does not send the credential on the stream yet and the gate does not read it, so a compromised device on a trusted address still passes this check. A stolen YubiKey on another host would pass the device check too; it is limited by low-risk scopes, voice plus challenge for anything higher, and one-step revocation |
| 19 | Lock, garage or alarm operated as an ordinary write, or through the automatic " Lock" retry | Home Assistant on/off calls naming a lock, garage, door or alarm (name, area or device class) are high risk; the retry gets its own decision | Partly: classification tested; retry wiring reviewed | A device named without those words is classified as a write |
| 20 | New or unknown tool treated as read | Unlisted tools default to write; read-only actions on write tools are listed explicitly | Yes | A tool misclassified as read in config is not gated |
| 21 | Gate failure or misconfiguration | Gate errors fail closed in enforce; an unknown mode falls back to monitor, never off; an unset threshold verifies no voice; any missing signal fails | Partly: mode, threshold and missing-signal cases tested; error handling reviewed | Monitor mode blocks nothing by design until rollout |
| 22 | Path injection through the client-supplied session id | Session and audio ids are validated to a plain token before they reach a file path | No | Sessions are still keyed by a client-supplied id |

Not gated yet: explicit location-preference commands are handled before the model and do not pass the gate. 38 voice gate tests (`server/test/test_voice_gate.py`, `server/test/test_voice_scripts.py`) and 31 device identity tests (`server/test/test_device_identity.py`, `speaker/test/test_device_identity.py`) run in CI.

## Attacks run (demo.py in delegation/ and policy/)

Expired-token replay; exchange without `may_act`; another agent presenting the user's token; sub-agent asking for write scope; sub-agent asking for an unregistered tool; plain exchange to strip `act`; borrowed actor token; handoff token sent to a tool; injected merge via sub-agent; injected merge via gateway; out-of-session read; approval replay and reuse on a different PR; token without `act`; forged signature; live tool token after the user token is revoked; re-exchange of a revoked lineage; revocation by an agent outside the chain; revoked agent's actor token; tool server revoking the handoff above it; escalation to the actor's delegation and to the grant from repeated tool reports; `sts:admin` requested through exchange; admin route with a non-admin actor token; stolen tool token without a proof, with another client's key, with a replayed proof, with a proof for another URI, with a stale proof; exchange without a proof and under another client's key; bound admin token sent as Bearer; revoked key; OPA down; PDP timeout; voice match below threshold; replayed voice (liveness fail); off-network voice; voice with no signals; high-risk voice write with confirmations off. All refused, each with a logged reason. 87 Python tests and 22 policy tests pass.

## Next controls, in order

1. Sender-constrained tokens to close #1: DPoP is built (partial: binds to a software key in the agent's process, no nonces, no rotation); mTLS-bound tokens (RFC 8705) come with B's SVIDs and finish it.
2. Workload identity for agents instead of client secrets (B) to close #6 and #13, and to move the DPoP key out of process memory.
3. A real approval channel with the call summary shown to the user (#7).
4. Device posture as a signed policy input for write-class tools (D); the speaker's device credential (#14) is the first such input once the gate reads it.
5. Central, append-only audit sink (#12).
6. Pushed deny list to every PEP, and a Keycloak admin-event feed into grant revocation, so #11 holds across processes and for hop 1.

## Voice gate rollout, in order

1. Calibrate the match threshold from enrolled voices (`scripts/calibrate_voice_threshold.py`), then check the logged scores from real turns in monitor mode.
2. Spoken confirmation for writes and phone approval through the Home Assistant app for high-risk calls and enrollment (#17, #19).
3. A spoken liveness challenge, then an anti-spoof model (#15).
4. Switch to enforce.
5. Gate the direct location-preference commands and move identity for per-person reads onto the gate (#16).
6. Send the device credential on the Converse stream and let the gate take device identity in place of the address check (#18); then move the key from the YubiKey to a secure element or SPI TPM on the next carrier-board revision (`DEVICE_IDENTITY.md`).
